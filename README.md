# Interactive Ride Wristband: IR Protocol Analysis and Transmitter

A personal engineering project to reverse engineer the infrared protocol used by
an interactive theme park wristband system, then design and build a wrist-worn
ESP32 transmitter that reproduces it.

The project covers signal capture, protocol analysis, hardware design, firmware
and validation testing.

**Status:** working. Every captured code is reproduced and responds as expected
at the receiver.

---

## Summary

- Captured pulse timings from the original attachments with a Raspberry Pi Pico
  and an IR receiver, and decoded a 28-unit frame on a 38 kHz carrier.
- Identified a three-field structure in the payload that explains every captured
  code, including one that combines two fields.
- Built a transmitter on an ESP32-C3 round touchscreen board, driving a 940 nm IR
  LED through a logic-level MOSFET stage.
- Validated the timing model three independent ways: logger capture, video
  analysis of an original attachment, and video analysis of this device.

## The protocol

### Frame structure

Every code uses the same 28-unit frame, transmitted on a loop with no gap
between repeats. One unit is roughly 32 ms.

```
Preamble   ON 3u, OFF 3u, ON 2u            8 units, identical for every code
Payload    10 cells x 2u                  20 units
             cell = 0  ->  OFF, OFF
             cell = 1  ->  OFF, ON
                                          28 units total, ~900 ms
```

The leading OFF in each cell is part of the encoding, not a separator.

### Physical layer

| Property | Value | How established |
|---|---|---|
| Carrier | **38 kHz** | Confirmed empirically at the receiver |
| Wavelength | 940 nm | Standard consumer IR; works |
| Receiver type | Demodulating | Implied by the carrier requirement |

### Captured codes

Cells numbered 1–10, left to right.

| Code | Lit cells | Unit | Loop |
|---|---|---|---|
| Code 1 | 3 | 31.75 ms | 889 ms |
| Code 2 | 2, 3 | 31.70 ms | 888 ms |
| Code 3 | 1, 2, 3 | 32.70 ms | 915 ms |
| Code 4 | 6 | ~32.2 ms | ~901 ms |
| Code 5 | 3, 5, 6 | ~32.2 ms | ~901 ms |
| Code 6 | 9 | ~32.2 ms | ~901 ms |
| Base (no attachment) | 5, 6 *(inverted)* | 32.75 ms | 917 ms |

Unit periods for codes 4–6 are estimates, derived from video rather than the
logger.

**The base code and the "no attachment" fault code don't sit on the cell grid.**
The base code emits ON-then-OFF per cell instead of OFF-then-ON, one unit early.
The fault code is three pulses at 5-unit spacing, which can't be expressed in
2-unit cells. Both are generated by the wristband itself rather than an
attachment.

### Clock tolerance

Unit periods vary by about 3% between attachments (31.70 ms for code 2 against
32.70 ms for code 3). These are uncalibrated RC oscillators, so the receiver must
already tolerate at least ±3%. Exact timing is not critical.

## Code structure

The rightmost lit cell of each code sits at 3, 6 or 9, exactly three apart. Read
as three fields, each extending **leftward** from its anchor:

| Field | Cells (anchor first) | Observed |
|---|---|---|
| A | 3, 2, 1 | values 1, 2, 3 (codes 1, 2, 3) |
| B | 6, 5, 4 | value 1 (code 4), value 2 (via code 5), value 3 unseen |
| C | 9, 8, 7 | value 1 (code 6), values 2 and 3 unseen |

**Code 5 shows that fields combine.** It is A = 1 plus B = 2, not a value of its
own, so the code space is 4 × 4 × 4 = 64, of which six attachment codes are known.

The base code's cells 5 and 6 are *consistent with* B = 2, but because it is
inverted and off-grid it isn't independent evidence for it.

### Cell 10 appears structurally unusable

Lighting cell 10 puts an ON in the final unit of the frame. Because frames repeat
with no gap, that runs straight into the next preamble's 3-unit ON and reads as a
4-unit one. This is a plausible explanation for why no code uses it.

## Validation

Three independent measurements agree, which is why the timing model is trusted.

**Pi Pico logger:** IR receiver sampled at 1 ms.

**Video analysis of an original attachment (code 1),** 98 frames at 29.97 fps,
fitting the model to per-frame LED brightness:

- Best-fit unit period **31.72 ms** against the logger's 31.75 ms, a 0.1% difference
- Correlation 0.947
- Sharp fit: ±0.2 ms drops it to 0.825, ±1 ms collapses it to 0.02
- Discriminates between codes: code 1 scores 0.947, every other code 0.68–0.85

**Video of this device** transmitting code 1: best fit 31.85 ms, r = 0.984.

A rolling-shutter test for the carrier was inconclusive: a phone exposing for
milliseconds averages over hundreds of 26 µs carrier cycles, so it could not have
detected a carrier even if present. The carrier was settled by testing at the
receiver instead.

## Hardware

### Display board

**Sunton/Guition ESP32-2424S012:** ESP32-C3-MINI-1U, GC9A01 240×240 round IPS,
CST816 capacitive touch, IP5306 charger, A6165P LDO.

| Function | GPIO |
|---|---|
| LCD SCK / MOSI / CS / DC | 6 / 7 / 10 / 2 |
| LCD RST | not connected (power-on reset only) |
| Backlight | 3 |
| Touch SDA / SCL / INT / RST | 4 / 5 / 0 / 1 |
| BOOT button | 9 |
| Free | 8, 20, 21 |

GPIO11–17 are internal SPI flash. GPIO18/19 are USB D−/D+.

The side switch is **not** a GPIO. It gates the battery rail at the IP5306's KEY
pin, so it can't be read or used to wake anything.

The 1.0 mm 4-pin side connector carries GND, 3V3, TX (GPIO21) and RX (GPIO20), so
the IR circuit plugs in with no soldering to the board.

### IR emitter

```
GPIO20 --[100R]--> gate, AO3400A (logic-level, Vgs = 2.5 V rated)
                   10k gate-to-source pulldown
source -> GND
drain  -> IR LED cathode
IR LED anode --[10R]--> 3V3
47µF + 1µF ceramic from 3V3 to GND, at the LED
```

940 nm, ~210 mA pulsed, 50% carrier duty. Visible on a phone camera at 3 m.

**The gate pulldown isn't optional.** A floating gate during boot lets the LED sit
half-on and can brown out the board.

**It must be a logic-level MOSFET** rated for full enhancement at 2.5 V or below.
IRLZ44N, IRF520, 2N7000 and BS170 don't switch properly at 3.3 V.

### Battery life

~500 mAh usable from a 600 mAh cell:

| Mode | Draw | Runtime |
|---|---|---|
| Transmitting, screen bright | ~48 mA | ~11 h |
| Transmitting, screen blanked | ~24 mA | ~21 h |
| Asleep | ~0.8 mA | 3–4 weeks |

**Expected IR load:** for code 1 the LED is on for 6 of 28 units (5 preamble + 1
payload). At 50% carrier duty and ~210 mA peak, that averages about **22 mA**
from the IR alone, and codes with more lit cells draw more. The transmit figures
above don't fully reconcile with this, so treat them as provisional until
re-measured.

## Firmware

`Band_IR_TX.ino`: Arduino, esp32 core 3.x, GFX Library for Arduino.

**Board settings:** ESP32C3 Dev Module, USB CDC On Boot **Enabled**, Flash 4MB,
Partition Default, JTAG Adapter Disabled.

### Controls

| Gesture | Action |
|---|---|
| Tap the top pill | 38 kHz carrier on/off |
| Tap left/right arrow, or swipe | Change code |
| Double-tap the middle | Start/stop transmitting |
| Swipe up/down | Trim unit period ±1% |
| Hold ~1.5 s | Sleep. Tap to wake. |

### Notable settings

| Define | Default | Purpose |
|---|---|---|
| `DUTY_CARRIER` | 128 | 50% of 255 |
| `CPU_MHZ` | 80 | Keeps APB at 80 MHz. **Don't go lower:** APB follows the CPU down and shifts the carrier |
| `LCD_ROTATION` | 1 | Display only |
| `TOUCH_SWAP_XY` / `FLIP_X` / `FLIP_Y` | true / true / true | Touch orientation, **independent of display rotation** |
| `TOUCH_DEBUG` | 0 | Prints raw and mapped coordinates, draws a dot |
| `ENABLE_PROBES` | 1 | Exposes untested candidate codes for hypothesis testing |
| `FLASH_GRACE_MS` | 15000 | Sleep refused after boot, so the board is always flashable |

### Design notes

**Deadline-based timing.** `waitUntil()` works from absolute microsecond
deadlines, so rounding never accumulates across a frame.

**Nothing draws to the screen mid-frame.** SPI writes take milliseconds and would
wreck the timing, so redraws happen between frames only.

**Gestures are decoded in software** from raw coordinates, not read from the
CST816S gesture register, because gesture firmware varies between panel batches.
Release requires two consecutive empty reads, since the controller occasionally
drops a report mid-touch.

**Anything that isn't a swipe counts as a tap.** An earlier version required
under 25 px for a tap and over 40 px for a swipe, silently dropping anything in
between.

**Recoverable with the case closed.** The BOOT button is unreachable once
assembled, so sleep is refused for 15 seconds after every boot to guarantee a
USB flashing window.

## Testing approach

- **Hypothesis testing with probe codes.** Untested cell patterns can be selected
  from the device to confirm or rule out the field model. A predicted code
  (field C = 2) was tested and produced no response, which is recorded as
  evidence against the model rather than discarded.
- **Timing trim.** The ±6% trim measures how much timing error the receiver
  tolerates.
- **Bench before assembly.** Gestures and IR output are checked before the case
  is closed.

## Building one

1. Buy an ESP32-2424S012 (touch variant); search that exact part number
2. Wire the IR circuit as above; it plugs into the 4-pin side connector
3. Install "GFX Library for Arduino" by moononournation
4. Flash with the board settings above
5. Bench-test the gestures before closing the case

**Bill of materials** beyond the display board: 940 nm IR LED, AO3400A (or
another MOSFET fully on at 2.5 V gate drive, such as the Si2302), 10R / 100R /
10k resistors, 47µF electrolytic, 1µF ceramic, JST 1.25 mm cable. A few pounds
all in.
