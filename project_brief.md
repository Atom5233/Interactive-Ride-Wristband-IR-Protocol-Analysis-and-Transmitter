# Interactive ride wristband IR transmitter — project brief

Full technical reference for a wrist-worn ESP32 device that reproduces the
infrared codes used by an interactive theme park wristband system and its
attachments.

**Status: working.** Code 1 confirmed at the receiver with a 38 kHz carrier.

---

## 1. The protocol

### Frame structure

Every attachment transmits the same 28-unit frame on a loop, with no gap between
repeats. One "unit" is roughly 32 ms, varying slightly by attachment.

```
Preamble   ON 3u, OFF 3u, ON 2u            8 units, identical on every attachment
Payload    10 cells x 2u                  20 units
             cell = 0  ->  OFF, OFF
             cell = 1  ->  OFF, ON
                                          28 units total, ~900 ms
```

The leading OFF in each cell is part of the encoding, not a separator. This is
why the original codes were written as 11 digits — the extra digit is padding and
the real payload is 10 cells.

### Physical layer

| Property | Value | Confidence |
|---|---|---|
| Carrier | **38 kHz** | Confirmed at the receiver |
| Wavelength | 940 nm | Standard for consumer IR |
| Modulation | Burst-modulated, receiver is demodulating type | Confirmed |

### Confirmed codes

Cells numbered 1–10, left to right.

| Code | Cells | Unit | Loop |
|---|---|---|---|
| Code 1 | 3 | 31.75 ms | 889 ms |
| Code 2 | 2, 3 | 31.70 ms | 888 ms |
| Code 3 | 1, 2, 3 | 32.70 ms | 915 ms |
| Code 4 | 6 | ~32.2 ms | ~901 ms |
| Code 5 | 3, 5, 6 | ~32.2 ms | ~901 ms |
| Code 6 | 9 | ~32.2 ms | ~901 ms |
| Base (no attachment) | 5, 6 *(inverted)* | 32.75 ms | 917 ms |

Unit periods for codes 4–6 are estimates — those codes came from video rather
than a logger.

**The base code and the "broken" no-attachment code do not sit on the cell grid.**
The base code emits ON-then-OFF per cell instead of OFF-then-ON, one unit early. The
broken code is three pulses at 5-unit spacing, which cannot be expressed in 2-unit
cells at all. Both are generated by the wristband itself rather than an attachment, and
are probably produced by different firmware. The broken code looks like a fault
heartbeat, not an ID.

### Clock spread

Unit periods vary by about 3% across attachments — 31.70 ms for code 2 against
32.70 ms for code 3. These are uncalibrated RC oscillators. **The receiver
must therefore tolerate at least ±3%**, which is why exact timing is not critical.
Aim for 32.2 ms if using a single value for everything.

## 2. Code structure

### Three fields of three cells

The rightmost lit cell of each code family sits at 3, 6 or 9 — spaced exactly
three apart. Read as three fields, each extending **leftward** from its anchor:

| Field | Cells (anchor first) | Observed values |
|---|---|---|
| A | 3, 2, 1 | 1 = code 1, 2 = code 2, 3 = code 3 |
| B | 6, 5, 4 | 1 = code 4, 2 = base code (consistent with, not proof), 3 = unseen |
| C | 9, 8, 7 | 1 = code 6, 2 and 3 unseen |

**Code 5 proves fields combine**: it is A=1 plus B=2, not a value of its own. So
the space is 4 × 4 × 4 = 64, of which 7 are in use.

### Cell 10 is unusable

Lighting cell 10 puts an ON in the final unit of the frame. Because frames repeat
with no gap, that runs straight into the next preamble's 3-unit ON and reads as a
4-unit one. This is very likely why nothing uses it.

### Seventh attachment code — unsolved

**Cells 8+9 (field C = 2) was tested at the receiver and did nothing.** That rules out
the simplest extrapolation. Remaining candidates, in order:

1. Cells 7, 8, 9 — field C = 3
2. Cell 8 alone, cell 7 alone — if cells stand alone rather than as fields
3. Cells 9, 10 — field C filling rightward instead
4. Cells 4, 5, 6 — field B = 3
5. Cross-field combinations, the same shape as code 5

**Search space:** 2 candidates if the missing code is a simple single-field value, 55 if
combinations are allowed, 503 if the field model is wrong entirely.

A single negative result is weak evidence. The receiver may need several
consecutive frames, or the tested scene may not respond to that code at all. Hold each
candidate for 5–6 seconds rather than passing through quickly.

## 3. Evidence

Three independent measurements agree, which is why the model is trusted.

**Pi Pico logger** (earlier capture work, before this build):
IR receiver sampled at 1 ms, giving the pulse timings above.

**Video of an original code 1 attachment**, 98 frames at 29.97 fps. Fitting the model
to per-frame LED brightness:

- Best-fit unit period **31.72 ms**, against the logger's 31.75 — a 0.1% difference
- Correlation 0.947
- Fit is sharp: ±0.2 ms drops it to 0.825, ±1 ms collapses it to 0.02
- Discriminates between codes: code 1 0.947, code 2 0.849, code 5 0.737,
  code 3 0.763, code 4 0.686, code 6 0.684

**Video of this device** transmitting code 1: best fit 31.85 ms, r = 0.984 —
a cleaner fit than the original attachment, because the LED blooms less across frame
boundaries.

**Rolling-shutter carrier test: inconclusive.** No banding found, but a phone
exposing for milliseconds averages over hundreds of 26 µs carrier cycles, and the
LED core saturates at 255 anyway. The test could not have detected a carrier even
if present. The carrier was settled empirically at the receiver instead.

## 4. Hardware — current build

### Display board

**Sunton/Guition ESP32-2424S012** — ESP32-C3-MINI-1U, GC9A01 240×240 round IPS,
CST816 capacitive touch, IP5306 charger with boost, A6165P LDO for 3V3.

| Function | GPIO |
|---|---|
| LCD SCK | 6 |
| LCD MOSI | 7 |
| LCD CS | 10 |
| LCD DC | 2 |
| LCD RST | **not connected** — power-on reset only |
| Backlight | 3 |
| Touch SDA | 4 |
| Touch SCL | 5 |
| Touch INT | 0 |
| Touch RST | 1 |
| BOOT button | 9 |
| Free | 8, 20, 21 |

GPIO11–17 are internal SPI flash and must never be touched. GPIO18/19 are USB D−/D+.

**The side switch is not a GPIO.** It gates the battery rail at the IP5306's KEY
pin. It cannot be read or used to wake anything, and USB power ignores it.

**The 1.0 mm 4-pin side connector carries GND, 3V3, TX (GPIO21) and RX (GPIO20)** —
so the IR circuit plugs in with no soldering to the board.

### IR emitter circuit

```
GPIO20 --[100R]--> gate of AO3400A (or BS170)
                   10k gate-to-source pulldown
source -> GND
drain  -> IR LED cathode
IR LED anode --[10R]--> 3V3
47µF electrolytic + 1µF ceramic from 3V3 to GND, at the LED
```

- 940 nm, 3 mm through-hole, Vf ≈ 1.2 V
- ~210 mA pulsed at 10 Ω
- Visible on a phone camera at 3 m

**Must be a logic-level MOSFET** rated at Vgs = 2.5 V. IRLZ44N, IRF520 and 2N7000
do not switch properly at 3.3 V.

**The gate pulldown is not optional** — a floating gate during boot lets the LED
sit half-on and can brown-out the board.

### Battery

600 mAh lithium cell on the JST 1.25 mm connector. **Check polarity with a meter
before plugging in** — these connectors are not standardised.

**Known risk: IP5306 low-load shutdown.** That chip family cuts its output when
draw stays below roughly 45 mA, which is power-bank behaviour. Transmit-with-screen-off
draws about 24 mA and sleep under 1 mA, both below that threshold. Test on battery
before relying on it.

### Battery life estimates

Assuming ~500 mAh usable of the 600 mAh nominal:

| Mode | Draw | Runtime |
|---|---|---|
| Transmitting, screen bright | ~48 mA | ~11 h |
| Transmitting, screen blanked | ~24 mA | ~21 h |
| Idle, screen blanked | ~21 mA | ~24 h |
| Asleep, touch wake on | ~0.8 mA | 3–4 weeks |

A realistic day of use — two hours transmitting, ten minutes of screen, rest asleep —
costs about 60 mAh, so 8–9 days between charges.

**The CPU, not the IR LED, dominates transmit current.** Of the 24 mA, roughly 19
is the processor spinning in `waitUntil()` and only 3.4 is the LED.

## 5. Firmware

`Band_IR_TX.ino` — Arduino, esp32 core 3.x, GFX Library for Arduino by
moononournation.

**Board settings:** ESP32C3 Dev Module, USB CDC On Boot **Enabled**, Flash 4MB,
Partition Default, JTAG Adapter Disabled.

### Key settings

| Define | Value | Purpose |
|---|---|---|
| `IR_PIN` | 20 | MOSFET gate |
| `CARRIER_HZ` | 38000 | Confirmed correct |
| `DUTY_CARRIER` | 128 | 50% of 255 |
| `CPU_MHZ` | 80 | Keeps APB at 80 MHz so LEDC is unaffected. **Do not go lower** — APB follows the CPU down and shifts the carrier |
| `LCD_ROTATION` | 1 | Display only |
| `TOUCH_SWAP_XY` / `FLIP_X` / `FLIP_Y` | true / true / true | Touch orientation, **independent of display rotation** |
| `TOUCH_DEBUG` | 0 | Set to 1 to print raw and mapped coordinates and draw a dot |
| `ENABLE_PROBES` | 1 | Exposes untested candidate codes after the captured ones |
| `FLASH_GRACE_MS` | 15000 | Sleep refused for this long after boot, so the board is always flashable |

### Controls

- Tap the top pill — carrier on/off
- Tap left/right arrow, or swipe left/right — change code
- Double-tap the middle — start/stop transmitting
- Swipe up/down — trim unit period ±1%
- Press and hold ~1.5 s — sleep. Backlight dips when armed. Tap to wake.

### Design notes

**Deadline-based timing.** `waitUntil()` works from absolute micros deadlines, so
rounding never accumulates across a frame.

**Input is polled inside the transmit loop**, but only when more than 5 ms remains
before the next edge. The carrier is generated in hardware, so an I2C read cannot
disturb pulse shape.

**Nothing draws to the screen mid-frame.** SPI writes take milliseconds and would
wreck the timing. Redraws happen between frames only. The backlight-dip cue when
sleep is armed is a single PWM register write, which is safe at any point.

**Gestures are decoded in software** from raw touch coordinates, not read from the
CST816S gesture register, because gesture firmware varies between panel batches.
Release requires two consecutive empty reads, since the controller occasionally
drops a report mid-touch.

**Anything that is not a swipe counts as a tap.** An earlier version required
under 25 px for a tap and over 40 px for a swipe, and silently dropped anything
between — which is why the carrier pill only worked sometimes.

### Known quirks

- Trim is on an easy gesture and gets knocked accidentally. One video showed the
  watch running at −1% because of a stray swipe. Check the meta line if timing
  looks off.
- `LCD_ROTATION` and the touch flags are deliberately independent. Changing one
  does not change the other.

## 6. Planned: rotating-bezel build

A rotating bezel replacing touch as the primary control.

### Bezel sensing — magnets and Hall latches

**Not an encoder.** Embed magnets around the bezel's inner circumference with
alternating north/south facing inward, and put two **latching** Hall sensors on the
PCB at its edge.

- Bipolar latches, not switches — a latch toggles on north and holds until south,
  giving clean square waves with no chatter
- Sensors offset by **half a magnet pitch** for quadrature, or any odd multiple
  (1.5 pitches, 2.5) if packaging demands
- `pitch = (π × magnet circle diameter) ÷ magnet count`
- Air gap 1–2 mm with 2 mm neodymium discs
- No gears, ~1.1 mm added height, no wear, sealable

### Detents

Ball and spring against V-grooves in the bezel, dive-watch style. 3 mm steel ball,
90° included angle, 0.6–0.8 mm depth, 2–4 N spring force. Symmetrical so it clicks
equally both ways.

**Use a detent-less encoder if going mechanical instead** — two detent systems at
different pitches fight each other and feel mushy.

Printed PLA detents wear quickly under a steel ball. Use PETG or nylon, or a metal
insert.

### Pin budget

Holding GPIO1 low puts the CST816 in reset without affecting the display, which
frees the touch pins. Available: **0, 4, 5, 8, 9, 21**.

Put the button on **GPIO9** — it is the boot-mode strapping pin, so holding the
bezel button while powering on enters download mode. That replaces the BOOT button
you lose when the case closes.

**GPIO35 does not exist on the C3** — the chip stops at 21. Any reference to it
comes from original-ESP32 demo code.

### Recovery with the case closed

Slide the power switch off, plug in USB. The board cold-boots on USB power and
esptool resets it into download mode over native USB. `FLASH_GRACE_MS` guarantees
the window. **Leave a wire pigtail on the EN pad** as insurance — EN is a hardware
reset, not a GPIO, and works regardless of firmware state.

## 7. Planned: carrier board

A round PCB under the display module carrying the IR emitters, Hall sensors, button
and battery switching. Full spec in `carrier_board_spec.md`.

**Key decisions:**

- Carrier diameter = display board diameter + 6 mm, so a ring is exposed for
  forward-firing LEDs
- Four IR LEDs, **1206 SMD with ≥50° viewing angle** — the wide angle is what
  widens the beam, not the LED count
- Run LEDs from the **5 V rail**, not 3V3, so the LDO is untouched. 75 Ω each for
  50 mA, 200 mA total
- Separate resistor per LED — parallel LEDs do not share current evenly
- **47 µF plus 100 nF** at the LED rail. 1 µF is not enough at 200 mA: the caps
  must supply ±100 mA for each 13 µs carrier half-cycle, which is 1.3 V of ripple
  at 1 µF against 30 mV at 47 µF

**Why not full custom:** the GC9A01's 0.5 mm-pitch FPC is the genuinely hard part,
and the display module already solves it. At 8 units the per-unit saving is nil and
you would spend ~£100 on revisions. Buy the hard part.

**If going custom anyway:** ESP32-C3 SuperMini (~£1.30) plus a GC9A01 breakout
module with an 8-pin header (~£5) avoids the FPC entirely. Ten signals needed, ten
pins available once touch is dropped. Choose C3 over S3 for power and because the
firmware already runs on it — unless you want animated LVGL, where the S3's PSRAM
and second core earn their keep.
